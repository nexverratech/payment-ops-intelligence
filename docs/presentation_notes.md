# Presentation notes

Speaker notes for `presentation/payment_ops_intelligence.pptx`, generated by `scripts/build_presentation.py` from the same text as the slides' notes. About 20–25 minutes for 16 slides, plus questions. Edit the script, not this file.

## 1. Payment Operations Intelligence

Good morning. This is a multi-agent AI system that answers one question payment operations teams ask every week: why did payment failures go up, and what should we do about it? Everything you will see runs on one Windows laptop: no cloud services, no paid APIs, no API keys. The data is synthetic, generated with a fixed seed, with an incident hidden in it, so we can check whether the system finds the truth.

## 2. Why did payment failures go up last week?

When the failure rate jumps, an analyst has to combine four kinds of evidence by hand: the transactions themselves, our own deployments, the providers' status notices, and history to know what normal looks like. That is slow, and it invites the classic mistake of blaming whatever changed just before, the last deployment, without checking. The dataset here has 492,996 synthetic payments over 90 days across four payment providers, with one large incident injected: Kestrel timeouts from 23 to 25 September. There is also a deliberate red herring: a deployment two hours before it.

## 3. One question in, a verified report out

Here is the whole flow. A question in plain English. The local LLM proposes a plan, which week and which providers, and code validates it. Three agents then analyse in parallel. The impact agent sizes the damage. The LLM writes the report from the computed findings only, and every sentence is checked before anyone sees it. If too much fails, the user gets a clearly labelled template report instead. On the laptop a full run takes about 17 seconds for a simple question, and 26 seconds is the median across the ten evaluation questions; almost all of it is the model writing.

## 4. Four rules shaped every design decision

Four rules drove every design decision. One: local only and free. The configuration refuses any non-local address, and the test suite blocks outbound network calls. Two: code computes, the LLM writes. The model never calculates a number. Three: the backend enforces access. Roles are checked on every API call, and the LLM has no say in it. Four: every claim is checked, including the numbers, the citations and causal wording.

## 5. Everything runs on one computer

The architecture. Everything sits inside the boundary of this one computer. The browser talks to the Streamlit dashboard, which talks only to the API. The API checks sign-in and roles, then runs the LangGraph workflow. Agents read the payment data through a read-only database login. History, accounts and the audit log live in a separate schema, written by a second login that cannot see payment data. The LLM is Ollama on the local GPU. Nothing crosses the dashed line; the only internet use is downloading software once, and GitHub CI, which is development tooling, not part of the app.

## 6. Six agents, each with a narrow job

Six agents, each with one job and a fixed list of tools it may call. The coordinator plans and assembles. Transaction intelligence compares this week with last. Pattern investigation finds anomaly windows and ranks hypotheses. Forecasting says what normal looks like next. Business impact sizes the damage with honest labels. Verification and policy trusts nothing: it recomputes figures from the database and checks every sentence. Every tool call is recorded, and every finding cites the calls behind it.

## 7. It found the hidden incident, and the timing

Did it work? Yes. Across all providers, the weekly failure rate rose from 2.88 to 3.85 percent, a statistically significant change, and Kestrel explains 98 percent of the extra failures. Zooming in, Kestrel's failure rate went from 2.73 percent to 23.07 percent between 23 September 14:00 and 25 September 01:00. The injected incident ran from 14:00 on the 23rd to 02:00 on the 25th, so the window is right to the hour at the start and one hour short at the end. 87 percent of the failures in the window were timeouts, which is exactly what was injected. Source: docs/evaluation.md, seed 42.

## 8. Hypotheses are ranked, never declared proven

This is the part I am proudest of. A deployment went out two hours before the incident. A naive system, or a tired analyst, blames it. Our pattern agent checks: after that deployment, did every provider get worse, as you would expect if our own software broke? No, only Kestrel did, and our software serves all providers. So the deployment is ranked 'unlikely'. The provider-side problem leads, with a score of 6, but it is still called 'leading, unconfirmed', and the next step is to ask Kestrel for their incident report. The system shows its reasoning and does not overclaim.

## 9. Every sentence the LLM writes is checked

How do we trust text from a 4-billion-parameter model? We don't, we check it. Every sentence must cite a finding, every number must appear in the finding it cites, dates must be inside the period, and causal or proof language is removed unless hedged. Key figures are recomputed from the database. If more than 30 percent of sentences are removed, the user gets the template report, clearly labelled. In the second evaluation run, 93.8 percent of sentences passed, and both prompt-injection attempts were handled safely.

## 10. Measured on ten questions with known answers

We measured the real model on ten fixed questions: six ordinary, two prompt injections, two out of range. Run 1 found a bug in my own prompt, which I will come to on the next slide. After the fix, run 2: the plan was right for all ten questions, the verified LLM report was used every time, and 93.8 percent of sentences passed. Detection, measured separately on eight different random datasets, never raised a false alarm and caught 14 of 16 incidents; the two misses are the deliberately tiny ones below the reporting threshold. Ten questions is a small sample, so these numbers are indicative.

## 11. What the evaluation taught us

Three honest lessons. First, a checker can be wrong too. The first time the real model ran, all four removed sentences were actually true; the checker misread a date as a number, among other things. Each case became a regression test. Second, my own prompt caused errors: it gave an example ID, and the model copied it when there were no hypotheses. Removing the example took invented IDs from four to zero. Third, what checking cannot catch: the model once copied a cost range correctly but attached it to the wrong time period. Numbers can be right while the meaning is wrong, which is why findings stay visible beside every sentence, and why human review of a sample is the next step.

## 12. Runs survive interruptions and stay bounded

Resilience. After every step, its output is saved as a checkpoint. When I stopped a run with Control-C while the model was writing, the resume reused the six finished steps and only re-ran the report, verification and finalize; it took 15.7 seconds instead of starting over. Checkpoints are plain JSON validated against the workflow's types, never unpickled objects, which avoids a class of vulnerability LangGraph's own checkpoint loader had. Every run is bounded by limits on time, steps, tool calls, LLM calls and concurrent runs.

## 13. Access is enforced by the backend, and recorded

Security. Local accounts, passwords hashed with scrypt at OWASP's parameters, sessions held on the server so logout and disabling take effect immediately, and a lockout after five wrong passwords. Four roles. Note the separation of duties: the admin manages accounts and reads the audit log but cannot run investigations. Someone else's investigation answers 'not found', so IDs cannot be probed. Every sign-in, investigation, account change and refusal goes into an append-only audit log; a database trigger blocks changes even by the owner, and a hash chain shows exactly which row was altered.

## 14. Built and tested like a product

Engineering. Nine phases, each finished only when its tests passed on my laptop: from 37 tests in phase 1 to 435 in phase 8, including tests against the real database and the real local model. The whole system also runs as a Docker image: non-root, ports on 127.0.0.1 only, and no container holds a password it doesn't need. A GitHub Actions workflow is written to run the tests, build the image end to end and audit dependencies on every push; it has not been run on GitHub yet, and I say that plainly.

## 15. Honest limits and what comes next

Honest limits. The data is synthetic and cleaner than real data, so real-world accuracy would be lower. The model evaluation is ten questions, indicative not precise. Right-numbers-wrong-meaning errors need human review to measure. If you ask about a provider that doesn't exist, the report quietly reviews all providers instead of saying so. Next: a larger model on my new PC with an RTX 5070 Ti, using the same evaluation so results compare directly; a human review sample; per-provider data scoping for analysts; and running CI on GitHub.

## 16. Demo

Now the live demo. I sign in as an analyst, ask what went wrong with Kestrel in the week of 21 September, and we watch the agents work. Then I show the verification panel and the evidence behind each sentence. Then I sign in as the admin to show that the Investigate tab is gone for that role, and verify the audit log's hash chain. If the live model is slow, the fallback is the CLI with --no-llm, which answers in under a second with the labelled template report. The full script is in docs/demo_script.md.
